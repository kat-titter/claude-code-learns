Learns in one turn.
Keeps it for good.

You correct the agent once and it keeps the lesson. Feedback in any chat becomes a short guideline in a Skill, the library organizes itself, and a weekly check looks for new skills that fill a gap. It is built only on what Claude Code already has: Skills, hooks, memory and scheduled tasks.

Learns fast

A correction becomes guidance in the same turn, written for the whole family of problems. A lesson that fits an existing skill is folded into it.

Notices its own mistakes

Hooks flag feedback, and the agent treats its own surprise and debugging as signals. It asks whether each lesson applies beyond the task, and audits the library weekly.

Stays light

Every session carries only skill descriptions, each short with its use case first, and one memory index. Bodies and notes load when a task calls for them, and scripts do the reading.

00the loop

  1. noticea correction, a preference, surprise at a result, or the agent's own bug
  2. generalizewhich family of problems is this? write for the siblings
  3. routea general skill, your style skill, project memory, or CLAUDE.md
  4. writethe gist in one line: what to do, the example, the date
  5. validateit parses, triggers on realistic prompts and handles a second case
  6. organizeone home per guideline; merge, split and compress on signals
  7. watchweekly: new skills upstream, gaps, health and footprint

01notice

Hooks are tiny scripts Claude Code runs at set moments. When your message reads like feedback, one adds a line of context: does this apply beyond the task? if so, route it. When a request shares rare words with a skill's description, another names that skill, because skills often go unused even when they fit. After each reply, a third jots any feedback into a lessons inbox, a quick notebook. The agent also counts its own surprise ("17 s a frame seems like a lot") and its own debugging as signals. Most messages trigger none of this.

03write the gist

---
name: macos-long-render
description: Keep long Mac jobs awake (renders, training, batch) so they don't stall
  overnight. Use when a job runs over an hour or ran far slower than its estimate.
---
- Wrap the job in caffeinate: `caffeinate -dimsu python3 job.py`.
  A steady rate that drops off a cliff overnight is sleep, not heat.
  (2026-06-28: "17s/frame seems like a lot")

The description is the trigger, so it opens with the use case and ends with the words people say. Each guideline says what to do, with the example and the reason: guidance the agent can weigh, not rules, and only what the agent does not already know. A second case folds into the same line.

04validate

  • The frontmatter parses in a YAML parser (claude plugin validate can pass with nothing checked); one that doesn't loads with no description.
  • Three realistic prompts load it and two near-misses don't (trigger-evals.py, old description against new, three runs each).
  • It loads in real sessions: trigger-misses.py shows, per skill, how often a request that matched it actually loaded it. In one library the answer was about 1 time in 5.
  • It handles a sibling case; a bundled checker proves it on a second input.
  • It traces to a real moment. Anything that doesn't stays in the inbox.

05organize and refactor

Every guideline has one obvious home, so the next lesson knows where to go. Before writing, find the section that already answers the question and extend its line. When the signs show, refactor in one pass:

  • two descriptions fire on the same prompt: merge
  • one skill answers several questions or passes ~200 lines: split by task
  • the same guideline sits in two skills: keep it in its owner, link from the other
  • personal taste in a general skill: move it to your style skill
  • a line no task has needed in months: archive it

audit-skills.py reports each sign, including the same advice in two skills, in well under a second.

06watch, weekly

A scheduled task runs skills-watch.py, which remembers what it saw and reports only what changed. The agent then reads just the new skills' descriptions and leaves at most five proposals. Installing and editing wait for your yes.

07loops and graphs

A loop makes one piece of work correct without you: a check a program can fail, a repair, a rule for when to stop. A graph decides which pieces exist, in what order, and where you sign off8. Without a loop you read every output; without a graph you approve every step. The step most setups skip writes each failure down as a rule for the next run. That step is this repo.

The weekly pass, drawn as a graph. Each arrow carries one named value, and each node has its own check.

  3. inboxnever loaded into a session
  4. the week's lines
  5. watchera script: audit flags, gaps, and whether last week's drafted text is in the library now
  6. a report
  7. weekly agentjudges what is new and drafts at most five changes, each in a lane
  8. drafts, grouped by lane

Proposals are gated by what a mistake would cost to undo, not by a confidence score:

lanewhatgate
opena wording line in a skill or memory note kept in git: one revertships on its check, if you opt in
evidencea skill description (it changes when the skill loads), a merge, a scriptits trigger test, or a run on last week's data, first
closedhooks, settings.json, CLAUDE.md, installs, deletions, anything that publishesyou, whatever the evidence

Measured in one person's harness: 103 workflows written over three weeks (Oct 15 to Nov 4, 2026, 138 runs), and the weekly pass three days after its last report.

the graph fan out to agents in parallel85 / 103 a schema on each agent's output79 / 103 saved and reused, not drawn fresh0 / 103 the loop an agent asked to run a test81 / 103 the script gates on the exit code0 / 103 a bounded repair cycle0 / 103 runs resumed, not rerun whole17 / 138 weekly proposals that landed0 / 4

The graphs were good: most fanned out, and most agents returned a fixed shape. The loops closed through the person. Agents were asked to run tests in 81 workflows, but no script read an exit code: where one gated, it gated on an agent's verdict. No script repaired a failing unit and tried again; whole workflows were rerun instead of resumed, one six times; and 21 reviews, audits and verify passes were each drawn fresh. The example skill workflow-design holds the rules, and its check-repair.js template is a working graph: units fan out, each is checked by exit code and repaired alone up to three times, and every repair that passes comes back as a candidate rule.

08stays light

What a session carries against what waits until it is needed, in one real library (2026-10-26, 22 skills):

carried every sessionloaded when a task needs it
skill descriptions17.2 KB skill bodies213 KB memory index11.0 KB memory notes226 KB

Memory keeps one fact per note and one line per note in its index. Scripts read every file; the agent reads their short reports and only the files they name.

09why it works

It borrows the brain's split between a fast learner and a slow one1, a split also proposed for intelligent agents2.

the brainthis setup
errors are monitored as they happen3the feedback hook, and the agent's own surprise and debugging
a fast store grabs what just happened1the lessons inbox
only tagged, salient or repeated moments last4promote what recurs or matters
what fits a schema consolidates within two days5fold a lesson into the section that owns it
offline replay consolidates6the weekly watch and tidy pass
downscaling keeps the system efficient7compress, merge, archive

10install

git clone https://github.com/kat-titter/claude-code-learns
cd claude-code-learns && ./install.sh --name yourname --dry-run
./install.sh --name yourname

It adds capture-lesson, prompt-practice, a yourname-style skill, a CLAUDE.md that routes feedback, an inbox and an index, and merges five small hooks into settings.json after a backup. Re-running is safe, and ./install.sh --uninstall undoes it. For the weekly watch, paste weekly-watch.md into a weekly scheduled task.
