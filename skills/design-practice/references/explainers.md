# Explainers: processes, methods, long arguments

Part of design-practice: read when a page explains a process, a loop or a method, or argues over many chapters.

- **Method pages: the plain story first, the full method one click away.** Each section opens with two or three plain
  sentences and its main figure; equations, code and side studies sit in one fold per section ("the full method") with
  a visible arrow. A DJ tool's process page went from 17,900 px to 5,700 px closed ("keep simple, less math (option to
  expand full math)", 2026-10-20). On a page whose blocks a script re-injects between marker pairs, fold whole blocks
  (opening and closing marker together), or the next build swallows the fold.
- **The hero shows the idea the summary states, and no geometry appears twice.** The top figure must read before any
  chapter: the key idea drawn plainly, with the summary under it putting the same idea in words; a punchline figure
  that needs the essay's setup goes where that setup ends (an essay's hero wound both tables into loops before
  anything explained them; then "i still dont understand how this connects?", so the hero became the three findings on
  one ring and the wound tables moved to the chapter that explains them, 2026-10-25). An explainer tile beside the real tiles goes (the card explains the real one), and so does a hero of
  traces the live figures below already show (each fact once, under Text; then "best hook figure illustrating key
  concept(s), punchline?").
- **Show a process's structure before its parts.** A loop gets one overview figure first (its steps as a ring, each
  with a picture and a timing, inputs from outside drawn as arrows in), then each step as an open row: title, the
  method in one line, the reason, then pictures laid out input to output. A separate in > method > out strip above
  those pictures only repeats them (an art piece's feed, 2026-10-26: "super confusing"; "input > method > output logic
  should be much more clear"; then "a bit repetitive. remember show dont tell"). A methods section reads as a tutorial: each step links
  its code at a pinned commit, grouped file first, then its functions, then its key parameters as chips that each
  link to the line that sets them, the chosen values highlighted and explained on hover ("key python files, key params
  in each file should be more clearly connected") (an art piece's feed, 2026-10-26: "like tutorial: link specific open source code.
  highlight key parameters, choices").
- **Each detail shows where it sits, and its reason points at what it explains.** In a long process, every detail
  row carries a small copy of the overview (a mini ring with its step lit) that stays in view while you scroll, on a
  rail that returns to the start; a reason sits under the pictures it explains, never a separate paragraph labelled
  "why" (an art piece methods, 2026-10-26: "show where detail is highlighting, organization of related/connected elements. show
  dont tell why"). A pointer earns its place only when it names one element and is anchored to it by measurement;
  a reason about the whole row is a plain note in neutral ink (same page, later: carets at hand-set percentages under
  gold rules drew "what is arrow pointing to?").
- **Keep the overview in view beside its details.** On wide screens a process overview (a ring of steps) can stay
  sticky beside the step rows and light the step being read, so overview and details read as one figure; check that
  no ancestor hides overflow, which silently stops sticky (an art piece's feed, 2026-10-26: "disjointed ... as scroll,
  highlight active section"). Give each of a step's three marks one home: its icon on the overview, its number and name
  on its row, and a line joining them; the overview turns so the current step faces the rows (same page, later).
- **Mark the start and the return of a loop by their own shapes.** Input steps that happen once get a chain marker
  (past > style code > endless pictures) with their own link lit, not the ring; the return is an infinity sign whose
  crossing is the hand-off (dream B becomes the next dream A), not the whole ring lit; a rail between steps carries
  arrowheads, not a plain line (an art piece methods, 2026-10-26: "why whole loop highlighted? ... appear like infinity symbol";
  "use arrow instead of simple line"). On the return, show the loop starting again (the overview turns on by itself, step after
  step, lap after lap) rather than lighting every step at once (same page, later: "show loop reset (loop of loops)"). A loop that feeds itself reads clearest as a chain of its own unit: each turn
  drawn as the same small ring between the output it starts from and the output it makes (A, turn, B, turn, next),
  fading into the infinity sign (same page, later: a figure-eight of two lobes read less clearly than "dream A > B,
  loop of loops").
- **Draw a mutual relation as one shape.** Two parts that act on each other read clearest as halves of one form (a
  yin and yang: one circle split by what they share, each half holding a small seed of the other) with two equal arrows
  for the two directions; two boxes with a coloured arrow each way read as sender and receiver (an art piece one-water diagram,
  2026-10-26: "should more clearly show how it's yin/yang, mutual interaction"). Fill the shape with the work's own
  material (its real water, not flat grey) and let the reader try each interaction in the figure, with a key in the
  figure's own marks (same diagram, later: "too basic, flat. interactions not clear").
- **A scorecard is a table you can see.** Claims scored in cards with pills, a found line and a caveat each read as
  wordy and wobble when a page's chip style leaks in; draw them as one table instead: a short verdict word, the claim
  in a few words, the evidence drawn (rows of dots for counts, one dot per model, points on an axis), and the caveats
  once, in the prose around it. Case: an essay's census scorecard (2026-10-25: "this figure is a lil wonky
  and unclear, too wordy").
- **One example in view, the rest one click away.** When a point comes with several examples or reasons, show the
  strongest one in full and fold the others under a summary that counts them ("three more of the table's predictions");
  an explorer opens on one worked search rather than an empty list. Case: an essay's hidden-elements chapter and
  its model explorer, which opens on the repressilator (2026-10-25: "better use of collapsable content. ex show
  one example, additions can be expanded. search biomodels and generate example to make it interactive").
- **Examples: as few as carry the point, inside the column they illustrate.** Pick the most distinct three or four,
  each next to the step it shows and aligned to that step's edges, never a loose grid after it (2026-10-26: eight
  example dreams cut to four and moved into the loop's last card; "need that many? located in best place? aligned
  well?"). Show each image once: a second copy only to connect two rows becomes alignment (put the result under its
  source).
